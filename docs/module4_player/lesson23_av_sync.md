# 第23节：音视频同步原理

## 本节能力目标
- **深刻理解音视频同步（A/V Sync）的本质**：理解时钟漂移、采样率误差对播放体验的影响。
- **掌握常见的同步策略**：区分“视频同步到音频”、“音频同步到视频”以及“同步到外部时钟”的适用场景。
- **实现以音频为准的同步算法**：学会在 C++ 中建立音频时钟，并动态调整视频渲染频率。
- **掌握 PTS 与 TimeBase 的深度换算**：能够准确地将解码后的时间戳映射到真实播放时间。

## 真实工程对应场景
- **播放器核心算法**：所有播放器（FFplay, IJKPlayer, ExoPlayer）最核心、最难调试的部分就是同步逻辑。
- **直播低延迟控制**：在直播场景下，如何保持音画同步的同时尽可能压缩缓冲延迟。

## 引言
到目前为止，我们已经实现了一个能流畅播放视频的窗口，也实现了一个能发出声音的程序。但如果你尝试同时运行它们，很快就会发现问题：由于解封装速度、解码耗时以及硬件时钟的微小差异，声音和画面会迅速“分家”，出现嘴型对不上、动作快于声音等尴尬情况。

**音视频同步**是多媒体开发的皇冠，本节课我们将学习如何通过“视频追赶音频”的策略，让两者完美对齐。

## 理论讲解

### 1. 为什么会不同步？
理论上，如果一个视频是 25fps，我们每 40ms 渲染一帧，应该能对上。但现实很残酷：
- **硬件频率漂移**：声卡的物理采样率可能名义上是 44100Hz，实际是 44099Hz 或 44101Hz。
- **系统调度延迟**：操作系统无法保证 `sleep` 或定时器的绝对精确。
- **处理耗时波动**：复杂帧（如高码率 B 帧）的解码耗时长，简单帧耗时短。

长期累积下来，微小的误差会放大成明显的感官滞后。

### 2. 同步策略选择
- **视频同步到音频 (Sync to Audio)**：**最常用方案**。人耳对声音的断续（Drop/Repeat）极其敏感，而人眼对画面的微小跳帧或延迟容忍度较高。因此，我们让音频顺着声卡的时钟顺其自然地播，视频根据音频播到哪了来决定自己是“快点跑”还是“等一下”。
- **音频同步到视频 (Sync to Video)**：很少用，声音会因为拉伸或跳跃听起来非常诡异。
- **同步到外部时钟 (Sync to External Clock)**：用于多路流同步等复杂场景。

### 3. PTS 与真实时间
`AVFrame->pts` 是一个整数，它的单位是 `stream->time_base`。
例如 `time_base` 是 $1/90000$，`pts` 是 $9000$，那么对应的真实播放时间就是 $9000 \times (1/90000) = 0.1s$。
在同步计算时，我们必须将所有时间转换为以**秒**为单位的双精度浮点数（double）。

### 4. 同步算法：视频追赶音频
核心逻辑如下：
1.  **建立音频时钟 (Audio Clock)**：每当音频解码并推送到声卡时，记录当前这一块数据的 PTS。**注意**：由于 SDL 内部有缓冲区，当前推送到 SDL 的数据并不会立即播放。准确的音频时钟应扣除缓冲区内的待播放时长：
    `audio_clock = current_frame_pts - (SDL_GetAudioStreamAvailable / bytes_per_second)`。
2.  **计算差值 (Diff)**：`diff = video_frame_pts - audio_clock`。
3.  **动态调整定时器**：
    -   如果 `diff > 0.04s`（视频太快）：视频跑过头了，让下一次定时器触发晚一点。
    -   如果 `diff < -0.04s`（视频太慢）：视频落后了，让下一次定时器早点触发，甚至设置最小延迟（如 1ms）快速渲染下一帧。

## 关键点总结
-   **音频是主，视频是从**。
-   **PTS 是灵魂**：没有 PTS，同步无从谈起。
-   **硬件时钟漂移**：同步的核心是解决不同硬件设备（显卡 vs 声卡）物理时钟不一致导致的长期漂移。

## 预期结果与验收标准

### 预期输出
-   观察 `sync_test.mp4`，表盘指针跳动的一瞬间，耳机里刚好传出“滴”的一声。

### 验收标准
-   音画感知上完全同步。
-   能够处理长时间播放后的时钟漂移。
-   无内存泄漏。

## 常见错误与排查
-   **画面一闪而过**：检查是否正确换算了 `time_base`，或者音频时钟更新逻辑有误。
-   **声音嘶哑**：通常是由于音频重采样配置不当（例如单声道源未强制转为双声道）。

## 面试延伸题
-   **问**：为什么不直接用 `SDL_GetTicks()` 作为基准？
-   **答**：因为物理硬件（声卡采样率）的时钟频率与 CPU 系统时钟往往不一致。单纯依赖系统时间，长时间播放必然会导致漂移。以声卡实际消耗数据的进度作为基准，是最贴合真实物理情况的。
