# 第26节：RTMP 推流与拉流

## 本节能力目标
- **掌握直播链路基础架构**：理解 Pusher、Server (SRS) 和 Player 之间的协作关系。
- **理解 RTMP 协议特性**：掌握 RTMP 在低延迟直播场景下的优势及基于 TCP 的传输机制。
- **实现 C++ 实时推流器**：能够使用 FFmpeg API 将本地文件通过 RTMP 协议推送到流媒体服务器。
- **掌握推流节奏控制**：理解并实现“根据 PTS 模拟实时流”的算法，防止网络拥塞。

## 真实工程对应场景
- **直播软件推流模块**：OBS、抖音/快手直播助手等工具的底层推流逻辑。
- **监控安防上云**：将 IPC 摄像头的码流通过 RTMP 协议推送到云端直播平台。

## 引言
到目前为止，我们所有的操作（解封装、解码、渲染）都是针对本地文件的。但在互联网时代，音视频的灵魂在于“实时传播”。

本节课我们将跨入流媒体（Streaming）领域。我们将搭建一个属于自己的流媒体服务器，并编写一个 C++ 程序，把我们之前处理好的视频“广播”出去，让其他人能通过网络看到你的直播。

## 理论讲解

### 1. 直播系统的“三驾马车”
一个最简直播系统包含三个角色：
1.  **推流端 (Pusher)**：负责采集音视频，编码后推送到服务器。
2.  **流媒体服务器 (Server)**：负责流的分发、协议转换和权限控制。
3.  **拉流端 (Player)**：负责从服务器获取流并解码渲染。

### 2. RTMP 协议 (Real-Time Messaging Protocol)
RTMP 是由 Adobe 公司开发的协议，目前是直播推流领域的事实标准。
-   **传输层**：基于 TCP，保证了数据的可靠性。
-   **封装层**：数据被拆分成小的 Chunk 进行传输。
-   **延迟**：通常在 1-3 秒，适合交互式直播。

### 3. SRS (Simple Realtime Server)
SRS 是一款国产的、高性能、现代化的流媒体服务器，支持 RTMP, HLS, WebRTC 等多种协议。在学习阶段，我们使用它作为本地测试中心。

### 4. 核心逻辑：从“写文件”到“写网络”
在 FFmpeg 中，向 RTMP 服务器推流的操作与写一个本地 FLV 文件几乎完全一致：
-   **格式**：必须指定输出格式为 `flv`（因为 RTMP 的载体通常是 FLV tag）。
-   **路径**：路径不再是 `/path/to/file`，而是 `rtmp://ip/app/stream`。

### 5. 推流节奏控制 (Pacing) —— 重点
读取本地文件是非常快的，几秒钟就能读完一个小时的视频。但网络推流必须是“实时”的。
-   **DTS 偏移处理**：很多视频文件的第一个 Packet 的 DTS 并不从 0 开始。在计算休眠时间时，必须记录 `first_dts`，并使用 `current_dts - first_dts` 得到相对偏移量，否则会导致推流开始时产生长达数秒的异常阻塞。
-   **流过滤**：RTMP/FLV 协议通常只支持一路视频流和一路音频流。在推流时，应通过 `codec_type` 过滤掉字幕、数据等无关流，防止推流失败。
-   **模拟实时**：在 `av_read_frame` 后，根据相对 DTS 偏移量和开始推流的系统时间差进行 `av_usleep`，模拟真实的实时生成速度。

## 关键点总结
...
-   **比特率统计**：在推流循环中累计发送的字节数，并配合系统时间，可以实时计算出当前的推流比特率（kbps），这对于监控直播质量非常有意义。
-   **RTMP 必须配合 FLV 封装使用**。
-   **Pusher 的职责是“准时”送达数据包**。
-   **SRS 是目前性价比最高的测试/生产流媒体服务器**。

### 实验1：实现简单的 RTMP 推流器
**目标：** 编写一个 C++ 程序，读取 `input.mp4` 并推送到 `rtmp://localhost/live/test`。

**核心逻辑解析：**
-   **初始化输出**：
    ```cpp
    avformat_alloc_output_context2(&ofmt_ctx, nullptr, "flv", out_url);
    ```
-   **推流频率计算**：
    ```cpp
    int64_t start_time = av_gettime(); // 记录起始微秒数
    // ... 在循环中
    int64_t now_time = av_gettime() - start_time;
    int64_t pts_time = av_rescale_q(pkt->pts, time_base, {1, 1000000});
    if (pts_time > now_time) {
        av_usleep(pts_time - now_time);
    }
    ```

## 常见错误与排查
-   **推流瞬间结束**：检查是否实现了 `av_usleep` 节奏控制。
-   **连接失败**：检查 SRS Docker 是否正常启动，端口 `1935` 是否被占用。
-   **ffplay 只有声音没画面**：RTMP 必须从关键帧开始推，检查输入文件的第一个视频包是否是 I 帧（通常 FFmpeg 会自动处理，但如果是切片推流需注意）。

## 面试延伸题
-   **问**：RTMP 协议基于 TCP，为什么不选 UDP？
-   **答**：RTMP 诞生之初为了保证复杂的信令交互（握手、连接、创建流）的绝对可靠性。虽然 TCP 存在队头阻塞问题，但通过增大缓冲区和 CDN 优化，其延迟已能满足大部分直播需求。对于极致低延迟（<500ms），业界现在更多转向基于 UDP 的 WebRTC。
